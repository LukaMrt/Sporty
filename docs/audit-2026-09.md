## 1. Synthèse

Sporty est un projet **nettement au-dessus de la moyenne** pour un projet perso : Clean Architecture réellement appliquée (ports en `abstract class`, IoC centralisé, dependency-cruiser en CI), use cases fins et testés unitairement (~700 tests Japa, 86 fichiers de spec), chiffrement AES-256-GCM des tokens OAuth, protection CSRF sur l'OAuth Strava via `state`, pipeline CI complète jusqu'au push Docker, et un domaine métier riche (VDOT Daniels, Banister CTL/ATL/TSB, zones Karvonen).

Les problèmes trouvés relèvent surtout de **trois familles** :

1. **Fuites et oublis de sécurité** : le hash du mot de passe part vers le navigateur sur les pages admin, pas de limitation de débit sur `/login`, CSP désactivée.
2. **Fonctionnalités "câblées mais inatteignables"** : toute la chaîne de recalibration automatique du plan (`session:completed` → `week:completed` → `RecalibratePlan`) ne peut en pratique **jamais** se déclencher depuis l'UI, et certaines de ses branches sont du code mort logique.
3. **Robustesse opérationnelle** : pas de transactions sur les écritures multi-lignes, scheduler en mémoire, stockage GPX non persisté en Docker, erreurs avalées sans log.

L'architecture n'a **pas** besoin d'être refondue : l'essentiel des corrections est local et peu risqué.

## 3. 🔴 P0 — À corriger immédiatement

### P0-1 · Le hash du mot de passe est envoyé au navigateur (pages admin) ✅

- **Où :** [users_controller.ts:29](../app/controllers/admin/users_controller.ts#L29) et [users_controller.ts:51](../app/controllers/admin/users_controller.ts#L51)
- **Cause :** l'entité domaine [`User`](../app/domain/entities/user.ts) contient `password`, et [`LucidUserRepository.#toEntity`](../app/repositories/lucid_user_repository.ts) le remplit avec le hash scrypt. Le controller passe ces entités **telles quelles** à `inertia.render(...)`. Inertia sérialise **toutes** les props dans l'attribut `data-page` du HTML : le `serializeAs: null` du modèle Lucid ne sert à rien puisqu'on a déjà converti en objet brut.
- **Impact :** tout admin (ou toute personne ayant accès à une session admin, une extension navigateur, un cache proxy…) récupère les hashs de **tous** les utilisateurs → attaque hors-ligne possible.
- **Correctif recommandé (en 2 temps) :**
  1. **Immédiat** : mapper vers un DTO dans le controller (`{ id, email, fullName, role, onboardingCompleted, createdAt }`), comme c'est déjà fait dans `SessionsController.index`.
  2. **Structurel** : retirer `password` de l'entité `User`. Le hash n'a rien à faire dans le domaine — `verifyPassword()` existe déjà dans le repository. Introduire un type `NewUser = Omit<User,'id'> & { password: string }` pour la création uniquement.
- **Test à ajouter :** un test fonctionnel qui vérifie que la réponse de `GET /admin/users` ne contient pas la chaîne `$scrypt$`.

### P0-2 · Aucune limitation de débit sur `/login` (et `/register`) ✅

- **Où :** [start/routes.ts](../start/routes.ts) — routes `POST /login` et `POST /register`.
- **Impact :** brute-force illimité des mots de passe. Combiné à la politique `minLength(8)` sans autre règle, c'est la principale surface d'attaque d'une instance exposée sur Internet.
- **Correctif :** installer `@adonisjs/limiter` (store `database` ou `memory` pour un mono-instance) et appliquer un throttle du type _5 tentatives / 15 min par couple (IP, email)_. Remettre le compteur à zéro après un login réussi.

### P0-3 · Suppression d'un utilisateur ayant un plan ou un objectif → erreur 500 ✅

- **Où :** [create_training_goals_table.ts:9](../database/migrations/1774256723690_create_training_goals_table.ts#L9), [create_training_plans_table.ts:9](../database/migrations/1774256724286_create_training_plans_table.ts#L9)
- **Cause :** `references('id').inTable('users')` **sans** `onDelete('CASCADE')` (défaut PostgreSQL = `NO ACTION`). Toutes les autres tables liées aux users (sessions, profils, connecteurs) ont bien la cascade.
- **Impact :** `DELETE /admin/users/:id` lève une violation de clé étrangère dès que l'utilisateur a utilisé le module Planning.
- **Correctif :** nouvelle migration qui drop/recrée les deux FK avec `ON DELETE CASCADE` (ne **pas** modifier les migrations existantes, déjà jouées).

### P0-4 · Les fichiers GPX sont perdus à chaque redéploiement Docker ✅

- **Où :** [local_gpx_file_storage.ts](../app/services/local_gpx_file_storage.ts) écrit dans `storage/gpx/…` → `/app/build/storage` dans le conteneur. [docker-compose.yml](../docker-compose.yml) ne déclare **aucun volume** pour ce chemin.
- **Impact :** `docker compose up --build` ou un pull de la nouvelle image efface tous les GPX ; `sessions.gpx_file_path` pointe alors vers des fichiers inexistants.
- **Correctif :** ajouter un volume nommé `gpxdata:/app/build/storage` et idéalement rendre la racine de stockage configurable (`STORAGE_PATH` dans `start/env.ts`). À terme, envisager `@adonisjs/drive` (FS local ou S3) derrière le port `GpxFileStorage`.

## 4. 🟠 P1 — Bugs fonctionnels importants

### P1-1 · La recalibration automatique du plan ne se déclenche jamais depuis l'UI ✅

C'est le constat le plus important côté métier. La chaîne prévue :

```
Séance créée/importée ──emit──▶ session:completed
                                   │
                    UpdateFitnessProfileListener
                    (toutes les séances de la semaine ≠ Pending ?)
                                   │ oui
                                   ▼
                             week:completed ──▶ RecalibratePlanListener ──▶ RecalibratePlan
```

**Pourquoi elle ne fonctionne pas :**

1. Le listener ne fait quelque chose que si la séance réalisée est **déjà liée** à une séance planifiée (`completedSessionId === sessionId`). Or la liaison ne se fait que via `POST /planning/sessions/:id/link` ([LinkCompletedSession](../app/use_cases/planning/link_completed_session.ts)), **et aucun composant frontend n'appelle cette route** (vérifié : seul `PUT /planning/sessions/:id` est utilisé, par `WeekDndView` et `EditSessionSheet`). Il n'existe pas non plus de liaison automatique à la création/import d'une séance.
2. La condition `allDone` ([update_fitness_profile_listener.ts:38](../app/listeners/update_fitness_profile_listener.ts#L38)) exige que **toutes** les séances de la semaine soient ≠ `Pending`. Or le statut `PlannedSessionStatus.Skipped` n'est **jamais écrit** nulle part dans `app/` (seulement lu). Une seule séance non faite bloque donc la semaine pour toujours.
3. Conséquence directe : `#deferMissedQualitySession` ([recalibrate_plan.ts:241](../app/use_cases/planning/recalibrate_plan.ts#L241)) cherche des séances qualité **Pending** de la semaine courante… alors qu'on n'arrive dans `RecalibratePlan` que si **aucune** n'est Pending. Cette branche est du **code mort logique**.

**Correctifs proposés (à arbitrer, c'est un choix produit) :**

- **Auto-liaison** : à la création/import d'une séance de course, chercher une séance planifiée `Pending` à la même date (± 1 jour) et la lier automatiquement. C'est le chaînon manquant principal.
- **Clôture de semaine par le temps** plutôt que par l'état : une tâche (scheduler existant ou calcul paresseux dans `GetPlanOverview`) qui, une fois la semaine écoulée, passe les `Pending` restantes en `Skipped` puis émet `week:completed`.
- Exposer dans l'UI le lien manuel (bouton "C'est cette séance-là") pour les cas ambigus.

### P1-2 · L'estimation VDOT à la hausse est polluée par les sorties vélo ✅ (latent)

> **Nuance après vérification :** la seule ligne de la table `sports` créée par le seeder est `running`, et aucune migration n'en ajoute d'autre. Tant qu'il n'y a pas d'autre sport en base, les imports vélo, natation, etc. finissent en `unsupported_sport` et ce bug ne se déclenche pas. Il devient réel **dès qu'un deuxième sport est ajouté**, ce que le mapping des deux connecteurs (cycling, swimming, walking, hiking) prépare déjà.

- **Où :** [`#getBestQualityPace`, recalibrate_plan.ts:281](../app/use_cases/planning/recalibrate_plan.ts#L281)
- **Cause :** on prend la meilleure vitesse moyenne parmi **toutes** les séances ≥ 3 km des 12 dernières semaines, **sans filtrer par sport**. Une sortie vélo à 30 km/h (500 m/min) est interprétée comme un 5 km couru à 2'00"/km → VDOT d'environ 85+.
- **Aggravant :** même en course, la vitesse moyenne d'un footing de 3 km est traitée comme une performance de 5 km "à fond" (`calculateVdot(5000, 5000 / bestPaceMs)`), ce qui mélange effort maximal et effort d'entraînement.
- **Correctif :** filtrer sur le slug `running`, et n'utiliser que les séances liées à des séances planifiées de type qualité (tempo/interval/repetition), ou mieux, les splits/segments issus du GPX. Même remarque pour `GetPlanOverview.#computeFitnessProfile`, qui agrège la charge de tous les sports (ça, c'est plutôt voulu pour la charge, mais à documenter).

### P1-3 · Calcul de la date d'une séance planifiée incohérent entre backend et frontend ✅

- **Frontend** ([Planning/Index.tsx:23-28](../inertia/pages/Planning/Index.tsx#L23)) : décalage calculé **relativement** au jour de début (`(dayOfWeek - startDow + 7) % 7`) → correct.
- **Backend** ([recalibrate_plan.ts:258](../app/use_cases/planning/recalibrate_plan.ts#L258)) : `start + (week-1)*7 + dayOfWeek` → suppose que le plan commence un **dimanche**. Or `GeneratePlan` démarre au lundi suivant (`nextMondayIso`), et les plans de transition/maintenance démarrent "aujourd'hui". Résultat : décalage d'un jour (et le dimanche tombe en début de semaine au lieu de la fin).
- **Correctif :** extraire **une seule** fonction `plannedSessionDate(startDate, weekNumber, dayOfWeek)` dans `app/domain/services/` et l'utiliser partout (backend) ; exposer la date calculée dans les props pour que le front n'ait plus à la recalculer.

### P1-4 · Effets de bord dans une requête GET (`GetPlanOverview`) ✅

- **Où :** [get_plan_overview.ts](../app/use_cases/planning/get_plan_overview.ts) — appelé par `GET /planning` **et** par `GET /planning/week/:weekNumber`.
- **Problème :** la simple consultation peut marquer le plan `completed` ou **créer un nouveau plan de maintenance complet** (des dizaines d'INSERT). Deux onglets/requêtes concurrentes → **deux plans actifs** créés. Un crawler/prefetch sur un GET peut modifier l'état.
- **Correctif :** séparer lecture et transition d'état. Option simple : un use case `AdvancePlanLifecycle` appelé explicitement (ou par le scheduler), protégé par transaction + verrou (`SELECT … FOR UPDATE` sur le plan). À défaut, a minima : transaction + index unique partiel (voir P2-2).

### P1-5 · Synchronisation Strava auto : fenêtre de 24 h seulement ✅

- **Où :** [sync_connector.ts:64](../app/use_cases/connectors/sync_connector.ts#L64) — `after: Date.now() - 24h`.
- **Impact :** si le serveur est arrêté plus de 24 h (maintenance, crash, laptop fermé en self-hosting), les activités de la période sont **définitivement ignorées** par l'auto-import.
- **Correctif :** utiliser `lastSyncAt` (déjà stocké !) comme borne `after`, avec un recouvrement de sécurité (ex. `lastSyncAt - 1h`) et un plafond (ex. 30 jours).

### P1-6 · Erreurs avalées silencieusement ✅

| Emplacement                                                                                                        | Effet                                                                                       |
| ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------- |
| [sync_scheduler.ts:70](../app/services/sync_scheduler.ts#L70) `catch {}`                                           | Aucune trace d'un échec de synchro.                                                         |
| [sync_connector.ts:130](../app/use_cases/connectors/sync_connector.ts#L130) `catch {}` par séance                  | La séance reste `New` → re-tentée **à chaque tick, indéfiniment**, sans log ni `setFailed`. |
| [get_plan_overview.ts:258](../app/use_cases/planning/get_plan_overview.ts#L258) `catch { return null }`            | Un bug de calcul de charge fait simplement disparaître le bloc fitness.                     |
| [strava_connector.ts:93](../app/connectors/strava/strava_connector.ts#L93) `catch {}` streams                      | Acceptable (dégradation voulue) mais mérite un `logger.warn`.                               |
| [strava_connector_controller.ts](../app/controllers/connectors/strava_connector_controller.ts) callback `catch {}` | Échec d'échange OAuth invisible dans les logs.                                              |

**Correctif :** introduire un port `Logger` dans le domaine (ou injecter le `Logger` Adonis dans les services d'infra) et journaliser systématiquement. Dans `SyncConnector`, appeler `importSessionRepository.setFailed(id, reason)` après N échecs.

### P1-7 · Le scheduler démarre pendant les tests ✅

- **Où :** [app_provider.ts:160](../providers/app_provider.ts#L160) — `['web', 'test'].includes(env)`.
- **Impact :** en test, des `setInterval` réels sont armés pour les connecteurs présents en base (seeders), pouvant déclencher des appels réseau vers Strava et rendre les tests non déterministes. `--force-exit` masque probablement le symptôme (process qui ne se termine pas).
- **Correctif :** ne démarrer qu'en `web`, ou piloter via une variable `SCHEDULER_ENABLED`.

## 5. 🟡 P2 — Robustesse, intégrité des données, sécurité secondaire

### P2-1 · Aucune transaction sur les écritures multi-lignes ✅

Seul `LucidUserProfileRepository` utilise `db.transaction`. La génération d'un plan (`GeneratePlan`, `GenerateTransitionPlan`, `GenerateMaintenancePlan`, `ResumeFromInactivity`, `RecalibratePlan`, `HandleVdotDownProposal`) crée 1 plan + N semaines + M séances **une requête à la fois** (N+1 INSERT, ~60–150 requêtes). Un crash au milieu laisse un plan actif **à moitié généré**.

**Correctif (compatible Clean Archi) :** ajouter un port `UnitOfWork` (`abstract run<T>(fn: () => Promise<T>): Promise<T>`) implémenté avec `db.transaction` + `AsyncLocalStorage` pour propager le `trx` aux repositories. Au passage, ajouter `createWeeks(batch)` / `createSessions(batch)` en `createMany` pour passer à 3 requêtes.

### P2-2 · Invariants métier non garantis par la base ✅

| Invariant                           | État                                                                      | Correctif                                                                             |
| ----------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 1 seul plan `active/draft` par user | vérifié applicativement seulement (race possible)                         | `CREATE UNIQUE INDEX … ON training_plans(user_id) WHERE status IN ('active','draft')` |
| 1 seul objectif `active` par user   | idem                                                                      | index unique partiel sur `training_goals`                                             |
| Pas de doublon de séance importée   | **aucune contrainte** sur `sessions(user_id, imported_from, external_id)` | index unique partiel `WHERE external_id IS NOT NULL`                                  |
| 1 seul admin initial                | `countAll()` puis `create()` → race sur `/register`                       | transaction + verrou, ou contrainte applicative via advisory lock                     |

### P2-3 · CSP désactivée ✅

[config/shield.ts](../config/shield.ts) : `csp.enabled: false`. Avec Inertia + Vite, une CSP stricte est faisable : `script-src 'self' 'nonce-…'` (Shield fournit `cspNonce`), `img-src 'self' data: https://*.tile.openstreetmap.org` pour Leaflet, `connect-src 'self'` (+ `ws:` en dev pour HMR). Commencer en `reportOnly: true`.

### P2-4 · Données dérivées contrôlées par le client ✅

Les validators de séance acceptent `sport_metrics: vine.object({}).allowUnknownProperties()` ([create_session_validator.ts](../app/validators/sessions/create_session_validator.ts)). Le client peut donc envoyer n'importe quel JSON, de taille arbitraire (jusqu'à la limite du body parser), y compris des valeurs normalement **calculées serveur** (`hrZones`, `trimp`, `cardiacDrift`).

- En création via GPX, le serveur fait confiance à la `heartRateCurve` renvoyée par le client au lieu de la relire depuis le fichier temporaire qu'il a lui-même parsé.
- En édition, le formulaire renvoie l'intégralité de `sportMetrics` (GPS track compris) : payload lourd, et toute altération côté client est persistée.

**Correctif :** schéma VineJS explicite pour les champs éditables ; recalculer les métriques dérivées exclusivement côté serveur à partir du GPX stocké (`gpx_temp_id` / `gpxFilePath`) ; en `update`, fusionner avec les `sportMetrics` existants plutôt que remplacer.

### P2-5 · Réinitialisation de mot de passe admin : pas d'invalidation de session 🔎

`ResetUserPassword` met à jour le hash sans vérifier l'existence préalable (l'erreur vient du repository) et **sans invalider** les sessions actives de l'utilisateur ciblé. Avec le store de session `cookie`, il est d'ailleurs impossible d'invalider côté serveur → envisager le store `database` ou `redis` si l'app est multi-utilisateurs.

### P2-6 · Admin : garde-fous manquants ✅

- Un admin peut supprimer **le dernier autre admin**, ou créer un utilisateur, mais `UpdateUser` ne permet pas de changer le rôle (incohérence avec `CreateUser`).
- `CannotDeleteSelfError` porte un message en français en dur, affiché tel quel en flash (non traduit).
- `role: data.role as UserRole` : utiliser `vine.enum(Object.values(UserRole))` pour supprimer le cast.

### P2-7 · Routes `/login` et `/register` sans middleware `guest` ✅

Le middleware `guest` existe mais n'est utilisé nulle part ; la logique "déjà connecté → redirige" est réimplémentée à la main dans `LoginController.show`. Appliquer `.use(middleware.guest())` et supprimer `LoginUser.isAuthenticated()`.

### P2-8 · Fichiers GPX temporaires jamais nettoyés ✅

`storage/gpx/tmp/` contient déjà **81 fichiers** en local. Chaque upload abandonné (formulaire non soumis) laisse un fichier. Ajouter une purge (> 24 h) au démarrage ou dans le scheduler. Idem : `EnrichSessionWithGpx` écrit le fichier **avant** la mise à jour en base → fichier orphelin si l'update échoue. `forceDelete` d'une séance ne supprime pas son GPX.

### P2-9 · Conflits de refresh token Strava 🔎

Chaque requête crée un nouveau `StravaHttpClient` avec les tokens lus en base. Si le scheduler et une requête utilisateur rafraîchissent **simultanément**, deux `refresh_token` concurrents sont envoyés ; Strava fait tourner le refresh token, l'un des deux peut devenir invalide → passage du connecteur en `Error`. Un simple verrou (mutex en mémoire par `userId+provider`, ou `SELECT … FOR UPDATE`) suffit en mono-instance.

### P2-10 · Échec transitoire du refresh = erreur permanente ✅

Dans `StravaHttpClient.#doRefresh`, **tout** `!response.ok` (y compris 500/503/429 de Strava) passe le connecteur en `ConnectorStatus.Error`, ce qui retire le connecteur du scheduler (`permanent_error`). Ne basculer en `Error` que sur 400/401.

## 6. Architecture & Clean Architecture

### Points forts

- Ports en `abstract class` utilisables comme tokens IoC : choix pragmatique et bien documenté.
- `providers/app_provider.ts` comme **unique** point de composition, avec imports paresseux.
- Controllers globalement minces, validators isolés, erreurs métier typées.
- dependency-cruiser en CI : rare et précieux.

### Fuites constatées ✅

| Fuite                                                        | Où                                                                                                                                                                                                                                                               | Recommandation                                                                                                  |
| ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Use cases importent `@adonisjs/core/services/emitter`        | `create_session`, `import_sessions`, `sync_connector`, `link_completed_session`                                                                                                                                                                                  | Utiliser le port `EventEmitter` **déjà existant** (utilisé par `RecalibratePlan`).                              |
| Listener importe `emitter` directement                       | `update_fitness_profile_listener.ts`                                                                                                                                                                                                                             | Idem.                                                                                                           |
| Erreur métier définie dans un use case                       | `NoActivePlanError` dans [toggle_auto_recalibrate.ts](../app/use_cases/planning/toggle_auto_recalibrate.ts), `ConnectorNotConnectedError` dans `list_pre_import_sessions.ts` ; `handle_vdot_down_proposal` importe un autre use case pour l'erreur               | Déplacer dans `app/domain/errors/`.                                                                             |
| Logique métier dans les controllers                          | `StravaConnectorController.callback` fait l'échange OAuth `fetch(...)` et lit `env` ; `show` calcule `stravaConfigured` et mappe les DTO en double ; `LoginController.login` restaure la locale via 2 repositories ; `LocaleController` persiste les préférences | Use cases `CompleteStravaOAuth`, `GetStravaConnectorPage`, `LoginUser` (qui renvoie la locale), `UpdateLocale`. |

## 7. Module Planning (moteur Daniels, recalibration)

En plus de P1-1 à P1-4 :

- **Formules** : `calculateVdot` et `derivePaceZones` implémentent correctement Daniels-Gilbert (1979) avec résolution quadratique directe — ✅ bon travail. Les zones sont exprimées en %VDOT ; noter que Daniels définit plutôt les zones en %vVO₂max / %FCmax ; un test de non-régression contre les tables officielles (VDOT 40/50/60) serait rassurant.
- **Commentaire faux** dans `RecalibratePlan` : « facteur de charge si delta négatif (-10 à -20 %) » alors que la condition est `delta < -20 %`. Soit le code, soit le commentaire est faux → à trancher.
- `goal?.targetDistanceKm ?? 42.195` : un plan sans objectif (maintenance) est recalibré comme une prépa marathon. Les plans de maintenance ont `autoRecalibrate: false` donc c'est latent, mais fragile.
- `daniels_plan_engine.ts` (764 lignes) : découper par phase (base / qualité / affûtage / transition / maintenance) et par responsabilité (volume, distribution des séances, génération d'intervalles).
- Dates : `todayIso()` en UTC (`toISOString`) partout. Avec `TZ=UTC` côté serveur, un utilisateur en France voit la "semaine courante" basculer à 1 h/2 h du matin le lundi. Stocker un fuseau utilisateur dans les préférences et calculer "aujourd'hui" dans ce fuseau (Luxon est déjà là).
- `GetPlanOverview` charge **365 jours de séances** à chaque affichage du planning pour calculer CTL/ATL. Mettre en cache (colonne `fitness_snapshot` sur le profil, recalculée sur `session:completed`) — c'est d'ailleurs ce que le nom du listener promettait.

## 12. Base de données & migrations

- FK sans cascade (P0-3), invariants non garantis (P2-2).
- **Deux migrations avec le même préfixe** `1772000000003_…` : l'ordre dépend du tri alphabétique. Ça marche, mais c'est piégeux (et les timestamps "ronds" écrits à la main laissent penser à des migrations créées hors `node ace make:migration`).

Toute requête `SELECT *` sur `sessions` (liste, dashboard, fitness 365 jours) les **charge et les désérialise**. Soit sélectionner les colonnes utiles dans les requêtes de liste, soit déplacer les courbes/traces dans une table `session_streams` (ou dans le fichier GPX déjà stocké).
- `LucidTrainingPlanRepository.findActiveByUserId` : `.first()` sans `orderBy` → non déterministe si l'invariant est violé.
- `LucidUserRepository.create` ignore `onboardingCompleted` fourni par l'appelant (dépend du défaut SQL).
- Seeders : `3_session_seeder.ts` (994 lignes de données réalistes) est **aussi exécuté en test** (`runnerHooks.setup` → `testUtils.db().seed()`). Garder un seeder minimal pour les tests, et mettre les données de démo derrière `app.inDev`.

## 18. Focus — Charge d'entraînement (CTL/ATL/TSB) & zones cardiaques

> Ajouté à la demande : « les données d'entraînement du profil (charge, etc.) ont l'air buguées ». **Oui, elles le sont** : 4 bugs cumulés, dont 2 majeurs.

### 18.1 Comment c'est calculé aujourd'hui

`CTL / ATL / TSB / ACWR` sont affichés sur **/profile/athlete**, **/planning** et utilisés par `GeneratePlan` / `EstimateVdot`. Chaque endroit **recopie** le même bloc (5 copies : [athlete_profile_controller.ts:131](../app/controllers/planning/athlete_profile_controller.ts#L131), `get_plan_overview.ts`, `estimate_vdot.ts`, `generate_plan.ts`, `update_fitness_profile_listener.ts`) :

```
séances des 365 derniers jours
  └─▶ TrainingLoadCalculator.calculate(input)   // TSS par séance, 3 branches :
        1. TRIMPexp  si input.heartRateCurve + maxHR + restHR
        2. rTSS      si input.avgPaceMPerMin + input.vdot
        3. RPE       si input.perceivedEffort
        4. sinon     0
  └─▶ BanisterFitnessCalculator                 // EMA jour par jour, τ = 42 j / 7 j
```

### 18.2 Bugs ✅ (vérifiés dans le code et par simulation)

**B1 — 🔴 Les branches FC et allure ne sont presque jamais atteintes.** Aucun appelant ne transmet `heartRateCurve`, et seul `generate_plan` transmet `vdot`. Le calcul retombe donc sur l'effort perçu… qui vaut `null` pour **toutes les séances importées de Strava** (et pour les saisies manuelles sans effort) → **TSS = 0**. Un utilisateur qui importe tout depuis Strava a un CTL/ATL de **0**, quel que soit son volume.

**B2 — 🔴 Échelle d'effort incohérente.** Le formulaire propose un effort de **1 à 5** (5 emojis, validator `min(1).max(5)`), mais `#calcRpe` est normalisé pour une échelle **1 à 10** (« 1 h à 7/10 = 100 TSS », coefficient 4,2). Toutes les charges issues de l'effort perçu sont donc **divisées par ~2**.

**B3 — 🟠 Pas de décroissance jusqu'à aujourd'hui.** La boucle EMA de [banister_fitness_calculator.ts](../app/services/training/banister_fitness_calculator.ts) s'arrête à la **date de la dernière séance**, pas à aujourd'hui. Après quelques jours de repos, ATL devrait chuter et TSB remonter (fraîcheur) : l'écran affiche au contraire l'état figé du dernier jour d'entraînement.

**B4 — 🟡 Mélange des sports dans la branche allure (latent, seul `running` en base).** Quand `vdot` est fourni (`generate_plan`), `avgPaceMPerMin` est calculé pour **toutes** les séances : une sortie vélo à 30 km/h a un _intensity factor_ ≈ 2 → rTSS ≈ ×4 par rapport à une course de même durée.

**Simulation** (4 sorties d'1 h/semaine pendant 12 semaines, dernière sortie il y a 5 jours, formules reprises du code) :

| Scénario                                   |    CTL |    ATL |     TSB |     ACWR |
| ------------------------------------------ | -----: | -----: | ------: | -------: |
| Tout importé depuis Strava (code actuel)   |  **0** |  **0** |       0 |        — |
| Saisie manuelle, effort 3/5 (code actuel)  |     21 |     25 |      −4 |     1,17 |
| Même effort ramené à l'échelle 1–10 (6/10) |     43 |     50 |      −7 |     1,17 |
| … + décroissance jusqu'à aujourd'hui       | **38** | **23** | **+15** | **0,61** |

La dernière ligne est la valeur attendue : l'athlète est **frais** (TSB positif) après 5 jours sans courir, alors que l'app affiche une légère fatigue ou zéro.

### 18.3 Incohérences secondaires

- **Deux TRIMP différents** : `calculateTrimp` (zones × coefficients 1–5, style Edwards) est stocké dans `sportMetrics.trimp` et affiché sur la page séance, tandis que la charge utilise `TRIMPexp` Banister (jamais atteint, cf. B1). Le TRIMP affiché ne correspond à rien dans CTL/ATL.
- **Zones figées à l'import** : `hrZones`/`trimp` sont calculés **une seule fois** (création / import / enrichissement GPX) avec la FCmax du moment. Si tu modifies ta FCmax ou ta FC repos, les anciennes séances ne sont **pas recalculées**. Pire, la page séance affiche des seuils en bpm **recalculés en direct** (`getZoneThresholdsBpm`) à côté d'une répartition % calculée avec les **anciens** seuils → affichage incohérent.
- **LTHR estimée à 88 % de FCmax** (et non de la FC de réserve) : acceptable comme approximation, mais c'est précisément une valeur qu'il faudrait pouvoir saisir.
- **VDOT confirmé stocké en session** (`session.put('confirmedVdot')`) : perdu à la déconnexion, et donc jamais utilisé pour la charge rTSS du profil.
- 5 copies du même calcul, dont un `catch { return null }` qui masque toute erreur.

### 18.4 Correctif recommandé pour la charge

1. **Un seul use case** `GetFitnessProfile(userId, asOf = today)` qui remplace les 5 copies.
2. **Utiliser les données déjà stockées** : `sportMetrics.heartRateCurve` (GPX/Strava) → TRIMPexp ; sinon FC moyenne + durée → TRIMPexp « mono-point » ; sinon allure **course uniquement** + VDOT **persisté** (colonne `vdot` sur `user_profiles`) → rTSS ; sinon effort perçu.
3. **Corriger l'échelle RPE** : `perceivedEffort * 2` avant la formule, ou recalibrer le coefficient à `3.5 * 60 / 100 = 2.1` (3,5/5 ≈ seuil).
4. **Faire tourner l'EMA jusqu'à `asOf`** (aujourd'hui) et **amorcer** CTL avec les 42 premiers jours plutôt qu'à 0 (sinon le premier mois sous-estime la forme).
5. **Stocker le TSS par séance** (`sessions.training_load`, `sessions.load_method`) calculé une fois, recalculé quand le profil physiologique change → plus besoin de charger 365 jours de JSONB à chaque affichage.
6. Afficher la **méthode** utilisée (FC / allure / ressenti) et un indicateur « charge estimée » quand on retombe sur le ressenti.
7. Tests : cas « séances Strava sans effort ⇒ CTL > 0 », « 7 jours de repos ⇒ ATL ↓ et TSB ↑ », « vélo exclu du rTSS ».

### 18.5 Proposition — zones cardiaques éditables et recalcul automatique

Aujourd'hui les zones sont des constantes (`ZONE_THRESHOLDS` : 50/60/70/80/90/100 %) appliquées à la FC de réserve (Karvonen) si la FC repos est connue, sinon à la FCmax. Rien n'est éditable hormis FCmax / FC repos.

**Modèle proposé :**

```ts
// app/domain/value_objects/heart_rate_zones_config.ts
type HrZoneMethod = 'karvonen' | 'percent_max' | 'lthr' | 'custom'

interface HrZonesConfig {
  method: HrZoneMethod
  lthr: number | null // pour la méthode 'lthr' (Friel)
  customBoundsBpm: number[] | null // 6 bornes croissantes [Z1min, Z1/Z2, …, Z5max] pour 'custom'
}
```

- Stockage : colonne JSONB `hr_zones_config` sur `user_profiles` (défaut `{ method: 'karvonen' }`).
- Une fonction de domaine unique `resolveZoneBoundsBpm(profile) → number[6]` ; **tout** le reste (`getZoneForHr`, `calculateZones`, affichage) consomme ces bornes en bpm. Ça supprime la dualité Karvonen / %FCmax dispersée dans `heart_rate_zone_service.ts`.
- **Recalcul automatique** :
  - _FCmax observée_ : proposer (pas imposer) la FC max la plus haute des 6 derniers mois si elle dépasse la valeur du profil (en ignorant les pics isolés : percentile 99 de la courbe, ou valeur tenue ≥ 10 s).
  - _FC repos_ : pas mesurable depuis les séances ; laisser la saisie manuelle (ou import montre plus tard).
  - _LTHR_ : estimable depuis une séance « seuil » de 20–30 min (moyenne FC des 20 dernières minutes × 0,95, protocole Friel).
- **Recalcul des séances existantes** quand la config change : use case `RecomputeSessionHrMetrics(userId)` (idéalement en tâche de fond) qui recalcule `hrZones`, `trimp` et le TSS stocké à partir des `heartRateCurve` déjà présentes. À déclencher depuis `UpdateProfile` / `AthleteProfileController.updateProfile`.
- UI : sur /profile/athlete, un sélecteur de méthode, un aperçu des 5 zones en bpm (barre colorée), des champs éditables en mode « personnalisé » avec validation de la monotonie, et un bouton « Recalculer depuis mes séances ».

## 19. Connecteur Open Wearables (#21)

> Audité sur `8b18bfd` : `app/connectors/open_wearables/*`, `ApiKeyConnectorController`, `ConnectorController`, `ConnectApiKeyConnector`, `DisconnectConnector`, `ThrottlingRateLimitManager`, fixtures et tests associés.

### 19.1 Ce qui est très bien fait 👍

- **Découplage multi-provider réel** : `ConnectorDescriptor` (oauth / api_key), routes génériques `/connectors/:provider`, registre comme **unique** point de résolution, un rate limiter **par provider**, et la distinction `isKnownProvider` / `registry.has()` qui renvoie 404 au lieu de 500. C'est exactement l'évolution que l'abstraction appelait.
- **Clé API vérifiée avant stockage** (`GET /users`), refus si la clé voit plusieurs utilisateurs (`AmbiguousConnectorUserError`) pour ne jamais rattacher des séances au mauvais athlète. La clé est chiffrée en AES-GCM comme les tokens Strava.
- **Déduplication des workouts** (montre + téléphone) avec élection déterministe et fusion des champs manquants : bien pensée, bien commentée, testée sur des données réelles (65 workouts → 36 séances).
- **`externalId` composite stable** (`ow:<startUtc>|<type>`), préfixé pour éviter toute collision avec les ids Strava, et qui permet de retrouver la séance sans endpoint `GET /workouts/{id}`.
- **Pagination par curseur avec 3 garde-fous** (fin de pages, curseur vide, curseur qui ne progresse pas), respect de `Retry-After`, backoff exponentiel.
- Nettoyage de la courbe FC (bornes plausibles, doublons, tolérance de fin) et **date locale** obtenue en découpant la chaîne, ce qui est correct puisque l'API renvoie `start_time` avec son offset (`2026-08-09T11:02:03+02:00`).

### 19.2 Problèmes & risques

**OW-1 — 🟠 Doublons entre Strava et Open Wearables.** ✅ La déduplication ne fonctionne **qu'à l'intérieur** d'Open Wearables. Si les deux connecteurs sont actifs (montre synchronisée vers Strava **et** vers Apple Health/HealthKit), la même sortie est importée deux fois avec deux `externalId` différents (`12345678` et `ow:…`). Or le commit justifie la déduplication précisément par le risque de **charge doublée**. Correctif : à l'import, chercher une séance existante du même utilisateur dont le départ est à ±2 min et la durée à ±10 %, **tous providers confondus**. Au choix : la lier (champ `alsoImportedFrom`), fusionner les métriques, ou marquer la ligne de staging comme `duplicate`.

**OW-2 — 🟠 Courbe FC tronquée sans avertissement.** ✅ `getAllPages` s'arrête après `DEFAULT_MAX_PAGES = 50` pages × 100 échantillons = **5 000 points**, **sans lever d'erreur ni logger**. Avec une montre qui échantillonne à 1 Hz (Garmin, Polar via Open Wearables), toute séance de plus de **~83 min** voit sa courbe coupée. Les zones, la dérive et le TRIMP sont alors calculés sur une partie seulement, et la dérive est particulièrement faussée puisqu'elle compare les deux moitiés. L'Apple Watch (≈ 1 point / 5 s) repousse la limite à ~7 h, d'où le fait que ça ne se soit pas vu. Correctif : calculer le plafond à partir de la durée (`ceil(duration_s / 100) + marge`), et en cas de dépassement lever une erreur ou au minimum logger et marquer la courbe `truncated: true`.

**OW-3 — 🟡 Déduplication à l'égalité stricte de l'horodatage.** ✅ `groupKey` compare `start_time` à la **milliseconde**. Deux sources qui démarrent à 1 s d'écart ne sont pas regroupées ; ce n'est pas le cas sur tes données, mais c'est fragile (montre vs téléphone, arrondis différents). Regrouper par type + chevauchement temporel (ou tolérance de ± 30 s), et aligner `encodeExternalId`, qui tronque déjà à la seconde.

**OW-4 — 🟡 Coût de `getSessionDetail`.** Pour **chaque** séance importée : re-téléchargement de 3 jours de workouts (paginés) puis de la timeseries paginée. Un import de 50 séances représente plusieurs centaines de requêtes sur un serveur auto-hébergé, lissées par le throttle à 120 req/min, donc plusieurs minutes de requête HTTP synchrone pour `/import/batch`. Pistes : mettre en cache les workouts du lot par journée, ou stocker le workout brut dans `rawData` au moment du staging (il y est presque déjà) et ne requêter que la timeseries.

**OW-5 — 🟡 Dégradations silencieuses.** Comme pour Strava (P1-6) : `catch {}` sur la timeseries, `catch {}` sur la révocation dans `DisconnectConnector`, et `getConnectionStatus` qui transforme **toute** erreur (réseau, 500, timeout) en `ConnectorStatus.Error`. Logger, et ne passer en `Error` que sur 401/403.

**OW-6 — 🟡 Métriques calculées une seule fois.** Les zones et le TRIMP ne sont calculés que si la FCmax est connue **au moment de l'import** (`context.maxHeartRate`). Si tu renseignes ta FCmax après coup, les séances importées gardent leur courbe mais n'auront jamais de zones. Même remède que §18.3 : `RecomputeSessionHrMetrics`.

**OW-7 — 🟠 Lien direct avec le bug de charge (§18, B1).** Open Wearables fournit la **courbe FC complète**, la meilleure source possible pour un TRIMPexp précis… mais le calcul CTL/ATL ne la lit pas, et `perceivedEffort` est `null` à l'import : ces séances comptent aussi pour **0 TSS**. Corriger B1 valorisera immédiatement ce connecteur.

**OW-8 — 🟢 Divers.**

- `ConnectApiKeyConnector` ne démarre pas le scheduler (même comportement que Strava : il faut activer l'auto-import dans les réglages). Documenter, ou activer l'auto-import par défaut.
- Aucune limite de tentatives sur `POST /connectors/:provider/connect` : l'app peut servir d'oracle pour tester des clés contre le serveur Open Wearables configuré. Le risque est faible, mais le limiter de P0-2 couvre ce cas en une ligne.
- `metrics` est construit avec un cast `as RunMetrics` alors que la séance peut être du vélo ou de la natation : le type `SportMetrics` devrait être une union discriminée par sport.
- `OPEN_WEARABLES_API_KEY_HEADER` a une valeur par défaut codée en dur dans le provider **et** une valeur dans `.env` : garder une seule source.
- Les séances non-course sont rejetées en `unsupported_sport` (seul `running` existe en base). C'est cohérent avec le périmètre actuel, mais l'UI de staging devrait les montrer grisées avec une explication plutôt qu'en échec.

| `auto` _(défaut)_ | FCmax (+ FC repos si dispo) | Karvonen si FC repos connue, sinon % FCmax                | Comportement actuel : aucune régression pour les profils existants.                                                                                          |
| `karvonen`        | FCmax + FC repos            | FCrepos + {50, 60, 70, 80, 90, 100} % × (FCmax − FCrepos) | La plus fidèle quand la FC repos est fiable.                                                                                                                 |
| `percent_max`     | FCmax                       | {50, 60, 70, 80, 90, 100} % × FCmax                       | Simple, surestime les zones basses chez les athlètes à FC repos basse.                                                                                       |
| `lthr` (Friel)    | FC seuil (LTHR)             | Z2 = 85 %, Z3 = 90 %, Z4 = 95 %, Z5 = 100 % de LTHR       | **Choix à arbitrer :** Friel n'a pas de plancher Z1 ni de plafond Z5. Proposition : plancher Z1 = 75 % LTHR, plafond Z5 = FCmax si connue, sinon 110 % LTHR. |
| `custom`          | —                           | 6 bornes saisies                                          | Doivent être strictement croissantes et comprises entre 30 et 250 bpm.                                                                                       |

Représentation commune : **6 bornes en bpm** `[Z1min, Z1/Z2, Z2/Z3, Z3/Z4, Z4/Z5, Z5max]`. Une FC sous `Z1min` est hors zone (0) ; au-dessus de `Z5max`, elle reste en Z5 (comme aujourd'hui).

### 21.3 Architecture

**Domaine**

- `value_objects/heart_rate_zones_config.ts` _(créé)_ : `HrZoneMethod`, `HrZonesConfig { method, lthr, customBoundsBpm }`, `ZoneBoundsBpm`, `DEFAULT_HR_ZONES_CONFIG`, `HrZonesIssue`.
- `services/heart_rate_zone_bounds.ts` _(à créer)_ : **module pur** qui n'importe que des types, pour que le **frontend puisse l'importer** et calculer l'aperçu en direct sans aller-retour serveur. Le front importe déjà `app/domain/value_objects/run_metrics` en chemin relatif, et Vite élimine les `import type`.
  - `computeZoneBounds(method, physio, config) → ZoneBoundsBpm | HrZonesIssue`
  - `resolveZoneBounds(config, physio)` : applique la méthode choisie, avec repli `auto`
  - `previewAllMethods(physio, config)` : un résultat par méthode, pour les cartes de l'aperçu
  - `validateZoneBounds(bounds)` : croissance stricte et plages plausibles
  - `getZoneForBpm(bounds, hr)`, `calculateZonesFromBounds(bounds, curve)`, `boundsToThresholds(bounds)` (format attendu par `HeartRateZonesChart`)
- `heart_rate_zone_service.ts` : les fonctions actuelles (`getZoneForHr`, `calculateZones`, `buildMonoZoneHrMetrics`, `getZoneThresholdsBpm`) deviennent des adaptateurs de `auto`, puis sont retirées une fois tous les appelants migrés.
- `entities/user_profile.ts` : champ `hrZonesConfig?: HrZonesConfig`. Il est optionnel pour ne pas casser les ~18 fichiers de tests qui construisent des profils à la main ; absent, il vaut `auto`.
- `interfaces/connector.ts` : `MappingContext` reçoit `hrZonesConfig?`, pour que les imports Strava et Open Wearables utilisent les zones de l'athlète.

**Infrastructure**

- Migration : colonne `user_profiles.hr_zones_config` en `jsonb`, nullable (`null` = `auto`).
- Modèle `UserProfile` + `LucidUserProfileRepository` : lecture et écriture du champ.

**Use cases** : pas de nouvel endpoint, les zones passent par le formulaire de profil existant (`PUT /profile`).

- `UpdateProfile` accepte `hrZonesConfig`. Il valide la config contre la physiologie **fusionnée** (nouvelles valeurs ou valeurs existantes) et lève `InvalidHeartRateZonesError(issue)`, par exemple quand on choisit Karvonen sans FC repos.
- Appelants à migrer vers `resolveZoneBounds(profile.hrZonesConfig, profile)` : `CreateSession`, `UpdateSession`, `EnrichSessionWithGpx`, `SyncConnector`, `ImportSessions` (via `MappingContext`), `StravaConnector`, `OpenWearablesConnector`, et `SessionsController.show` pour `hrZoneThresholds`.

**HTTP**

- `update_profile_validator` : `hr_zones_method` (enum), `lthr` (entier 100–230, nullable), `hr_zones_custom_bounds` (tableau de 6 entiers, nullable).
- `ProfileController` : mapping de l'erreur de domaine vers une erreur de champ traduite (`profile.hrZones.errors.<issue>`).

### 21.4 Interface (page Profil, sous « Paramètres physiologiques »)

- Composant `inertia/components/Profile/HeartRateZonesEditor.tsx`, intégré au **même formulaire** que FCmax et FC repos : modifier la FCmax met **instantanément à jour** tous les aperçus.
- Une **carte par méthode** : nom, une phrase d'explication, une **barre colorée de 5 segments** (couleurs de `HeartRateZonesChart`) avec les plages en bpm. Une méthode indisponible est grisée avec la raison (« Renseigne ta FC repos »). La carte `auto` indique la méthode réellement appliquée.
- Méthode `lthr` : un champ LTHR s'affiche, avec un lien vers le guide physiologique (protocole de test de 30 min).
- Mode **manuel** : un bouton « Personnaliser à partir de cette méthode » copie les bornes de la carte sélectionnée dans 6 champs présentés en lignes `Z1 [min] – [max]`, où la borne haute d'une zone est la borne basse de la suivante. La validation se fait côté client avec la même fonction de domaine, et côté serveur.
- Accessibilité : les cartes sont des `radio` (`role="radiogroup"`), navigables au clavier.
- Traductions à ajouter : `profile.hrZones.*` (FR + EN).

### 21.5 Recalcul des séances existantes

Les zones, la dérive et le TRIMP sont **stockés** dans `sportMetrics` à la création ou à l'import (cf. §18.3). Sans recalcul, changer de méthode n'affecte que les **nouvelles** séances, et la page séance affiche des seuils actuels à côté d'une répartition calculée avec les anciens.

- Use case `RecomputeSessionHrMetrics(userId)` : pour chaque séance possédant une `heartRateCurve`, recalculer `hrZones`, `trimp` et `cardiacDrift` ; pour une séance avec seulement une FC moyenne, refaire le calcul mono-zone.
- Déclenchement : après un `UpdateProfile` qui modifie FCmax, FC repos ou la config de zones. Traitement asynchrone recommandé (plusieurs centaines de séances JSONB), par exemple via un événement `profile:hr_changed` consommé par un listener.
- À coupler avec la correction de la charge (§18.4) : le TSS stocké par séance devra lui aussi être recalculé.

### 21.6 Tests à prévoir

- Unitaires (domaine) : bornes de chaque méthode sur des valeurs de référence, repli `auto`, méthodes indisponibles, validation des bornes manuelles (égalité, ordre décroissant, hors plage), `getZoneForBpm` aux frontières.
- Use case : `UpdateProfile` refuse Karvonen sans FC repos, et accepte une config manuelle valide.
- Fonctionnel : `PUT /profile` enregistre la config et la page séance utilise les nouveaux seuils.
- Non-régression : un profil sans config donne **exactement** les mêmes zones qu'aujourd'hui.

### 22.3 Principe directeur : une couche « métriques quotidiennes »

La plupart des fonctionnalités reposent sur la même brique : une table **`daily_metrics(user_id, date, …)`** alimentée par un job (webhook ou tâche planifiée), qui contient par jour :

- la charge du jour (TSS), CTL, ATL, TSB, ACWR ;
- la FC repos, la HRV RMSSD, le sommeil (durée, efficacité, score), les scores OW et constructeur ;
- les pas, les minutes d'intensité, le poids.

Chaque graphique lit alors quelques centaines de lignes au lieu de recalculer sur 365 jours de JSONB, ce qui règle aussi le problème de performance de §12. C'est le **premier chantier technique** après la correction de la charge.
